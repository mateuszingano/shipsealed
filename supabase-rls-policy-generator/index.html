What the generated SQL does, and why

    
    
      
  • RLS in the same migration as the table. A table in an exposed schema is reachable with your public anon key the moment it exists. Why a table with RLS off is public.
    • 
      
  • One policy per operation, named to a role. INSERT gets with check, UPDATE gets using and with check so nobody can hand a row to someone else, and UPDATE always has a SELECT policy, without which it silently changes nothing.
    • 
      
  • (select auth.uid()) so Postgres evaluates it once per query, not once per row.
    • 
      
  • Explicit grants, only what's needed. New tables no longer get grants for the API roles; without one you get 42501 permission denied. Never grant ... on all tables: it also opens every table with RLS off.
    • 
      
  • Teams through a helper function. A policy that queries the membership table through RLS loops into 42P17 infinite recursion. The helper is security definer, lives in a schema the API doesn't expose, and only returns the caller's teams.
    • 
    

    
Tested: each pattern is applied to Postgres and checked as a signed-out visitor and as two users (own rows only, no cross-user reads or writes, no reassigning rows, no recursion on the membership table).
