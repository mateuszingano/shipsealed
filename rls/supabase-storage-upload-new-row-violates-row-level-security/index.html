Storage upload fails: new row violates row-level security policy

Postgres 15 · Supabase Storage✓ code tested against a real database
TL;DR

Every file is a row in storage.objects, and RLS is on there. With no INSERT policy that matches the path, the upload is refused with 403. Add an INSERT policy for the bucket that ties the first folder to auth.uid(), and upload to <user id>/file. Replacing a file (upsert: true) also needs SELECT and UPDATE policies.

01 What the error is

The Storage API turns the Postgres error into HTTP 403:

response

{ "error": "Unauthorized", "message": "new row violates row-level security policy" }

An upload inserts a row into storage.objects (bucket, path, owner). That table has RLS enabled, and by default no policy lets anyone insert, so every client upload is refused until you add one. Making the bucket public doesn't change this: "public" only affects downloads.

02 The policy: users upload into their own folder

migration.sql

create policy "users upload to their folder" on storage.objects
  for insert to authenticated
  with check (
    bucket_id = 'avatars'
    and (storage.foldername(name))[1] = (select auth.uid())::text
  );

storage.foldername(name) returns the folders in the path, so for <user id>/avatar.png the first one is the user id. The upload has to use that path:

upload.ts

const { data: { user } } = await supabase.auth.getUser();
await supabase.storage.from('avatars').upload(`${user.id}/avatar.png`, file);

03 Why it still fails

CAUSE 1

The path doesn't start with the user id

A file at the bucket root (avatar.png) has no folder, so the check is false. So does another user's folder.

CAUSE 2

Not signed in

The client calls as anon, so auth.uid() is null and a policy to authenticated doesn't apply.

CAUSE 3 · upsert

Replacing a file with upsert: true

Overwriting an existing path is an insert that turns into an update, and Postgres requires matching SELECT and UPDATE policies as well. With only the INSERT policy, the upsert is refused even for a path that doesn't exist yet.

migration.sql (only if you use upsert or read the files back)

create policy "users read their folder" on storage.objects for select to authenticated
  using (bucket_id = 'avatars' and (storage.foldername(name))[1] = (select auth.uid())::text);

create policy "users update their folder" on storage.objects for update to authenticated
  using (bucket_id = 'avatars' and (storage.foldername(name))[1] = (select auth.uid())::text);

04 Prove it

✗ no INSERT policy  → new row violates row-level security policy
✓ A uploads to A/me.png  → ok
✓ A uploads to B/x.png, to the root, or to another bucket  → refused
✓ upsert with INSERT only, then INSERT + UPDATE  → refused; with SELECT too → ok

Don't "fix" it with with check (true): that lets anyone with your public anon key write anywhere in the bucket.

FAQ

I made the bucket public. Why do uploads still fail?

Public only means files can be downloaded without a token. Uploads, updates and deletes still go through the RLS policies on storage.objects.

Can I upload with the service_role key instead?

From a server, yes: it bypasses RLS. Never from the browser, where the key would be exposed. For user uploads, a scoped INSERT policy is the right tool.
